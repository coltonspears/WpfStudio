# WpfStudio

A native Windows IDE focused on WPF, C#, CommunityToolkit.Mvvm, and SQL Server. It combines a dockable editor with an isolated Roslyn/MSBuild worker, debugging, an embedded terminal, WPF navigation, NuGet packages, Git, a SQL workbench, and the ColtonGPT assistant.

See the [XAML feature tour](docs/xaml-feature-tour.md) for screenshots of diagnostics, preview scenarios, live binding inspection, layout, appearance, and reviewed source edits.

The current XAML milestone includes the implemented authoring, preview, and inspection workflows below. [Validation results](VALIDATION.md) record the tested scope; the [remaining designer roadmap](docs/xaml-devtools-design.md#full-goal-acceptance-ledger) tracks future work, including broader XAML language coverage, reparenting and toolbox composition.

## Run from source

Use Windows 11 x64 with the [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0). Install the Windows Desktop runtimes needed by the applications you develop; .NET 8, 9, and 10 projects can select their SDK through `global.json`. The full Visual Studio IDE is not required.

The terminal needs the free [Microsoft Edge WebView2 runtime](https://developer.microsoft.com/microsoft-edge/webview2/). PowerShell 7 is preferred when installed; Windows PowerShell and Command Prompt also work. Git integration uses an installed `git` command and its existing authentication configuration. ColtonGPT requires your OpenRouter API key and a model your account can access. SQL tools require access to a SQL Server instance. SQL Server LocalDB is optional and enables the database integration test.

```powershell
dotnet restore WpfStudio.sln
./tools/Get-Debugger.ps1
dotnet build WpfStudio.sln
dotnet run --project src/WpfStudio.App
```

Pass a workspace path to open it at launch:

```powershell
dotnet run --project src/WpfStudio.App -- C:\Work\MyApp\MyApp.sln
```

`Get-Debugger.ps1` downloads netcoredbg 3.2.0-1092 and verifies the pinned archive checksum. Terminal JavaScript assets are already included; installing Node.js or npm is unnecessary.

The IDE opens `WpfStudio.App.MainWindow`, resolved and shown by `App.OnStartup` in `src/WpfStudio.App/App.xaml.cs`. Its content is defined in `MainWindow.xaml`. WpfStudio draws its own title bar with `WindowChrome` (menu, command center, and caption buttons); Windows still provides the resize border, rounded corners, and shadow, and the maximize button supports Windows 11 Snap Layouts. Because the title bar is WPF content, the smoke-test screenshots include it. Theme and docking layout are restored from your local profile. The startup-project selector inside the IDE selects the application to run or debug, rather than the IDE's own window.

## Daily workflow

**Work with named elements.** `ElementName` completion offers declarations in the current authored namescope. Hover and **F12** explain and navigate the selected name; diagnostics catch invalid, duplicate and conflicting declarations. A page-local spelling warning can offer a checked **Ctrl+.** correction. Directly add, remove or rename a named element, or change its control type, and supported evaluated WPF pages update C# field completion, diagnostics and definitions from the current XAML without a build. **Find References** and reviewed **Rename** connect supported declarations to their authored C# uses. Undo, discard and language-worker restart derive fields from the resulting source buffers. These are in-memory editor declarations; generated files on disk and running applications remain governed by actual builds. Template scopes remain separate, and runtime-dependent names stay unresolved. See [named-element authoring and limits](docs/xaml-named-elements.md).

**Preview data and states.** Build the project, open a XAML Preview, choose a named **Scenario**, then **Refresh** to show project-provided data. A `wpfstudio.preview.json` file names data factories and optional compiled view factories for constructor dependencies. Factories run in fresh isolated preview processes. Source mode also supports common `d:` values and property elements, identified as a **design baseline** in the inspector. The bundled CounterApp includes Initial, Counted and Large count scenarios. See [preview data and scenarios](docs/xaml-preview-scenarios.md) for configuration, DI examples and supported design-time declarations.

**Start.** The Start page lists recent workspaces, opens the bundled CounterApp sample in one click, and shows a short getting-started checklist. The command center in the title bar (or **Ctrl+P**) finds files with fuzzy matching; type `>` or press **Ctrl+Shift+P** to run any command, with its shortcut shown beside it.

**Open and navigate.** Open a `.sln`, `.slnx`, or SDK-style `.csproj`. The solution tree uses vector icons for projects, folders, C#, XAML, and other files. Use quick-open for a filename and solution search (**Edit > Find in workspace**) for text. Every editor tab has a context bar showing the file's folder and kind, and the files related to it: a view's code-behind and view model, or the views that declare a view model as their `DataContext`. Press **F7** to jump between them. Right-click a tree item to open its project file, select the startup project, manage packages, reveal its folder, or copy its path. Keep an eye on Output when SDK discovery or restore fails: files remain accessible even if language services cannot fully load the project.

**Edit and refactor.** C# completion, signature assistance, definitions, references, rename, and formatting run through the worker. Right-click in the editor or press **Ctrl+.** to open its actions. Refactor includes symbol rename, organize usings, and switching a local declaration between `var` and an explicit type. These changes are previewed, checked against current document versions, and undoable. Type conversions reject cases that could change meaning; organizing usings avoids moving comments or conditional directives.

**Edit XAML.** Completion and live diagnostics use the owning project's C# compilation, including inherited, partial, referenced, and generated Toolkit properties. Declare a design type with `d:DataContext="{d:DesignInstance Type=vm:CustomerViewModel}"`, an object-valued `DataContext`, or a typed `DataTemplate`. Supported paths include dotted members, common indexers/collection items, ElementName, RelativeSource and local static sources. Hover shows type information, **F12** opens available source definitions, and **Ctrl+. > Quick fixes** offers checked, undoable binding spelling corrections. XML syntax, resolved control types, properties/events and attached properties also receive diagnostics; enum/bool values and project namespaces have completion. Unsaved XAML and open C# changes refresh analysis without building or running the app. For a linked XAML file, choose **Project** in the editor context bar to select the compilation used for completion, diagnostics, hover, definitions and fixes. Changing that context invalidates old suggestions and fixes. Unselected or ambiguous contexts, unknown runtime DataContexts, dynamic members and unsupported source/path forms remain uncertain. Local framework/resource suggestions remain available when the worker is unavailable.

**Use shared binding sources.** A supported `StaticResource` binding source or DataContext can use a declared object from evaluated project dictionaries, including linked files, referenced projects and the owning application resources. Unsaved dictionary changes refresh dependent completion, diagnostics, hover and definitions without editing the view. Ordinary editor requests read the needed dictionary imports while retaining the full evaluated resource catalog, so unrelated views do not exhaust the resource text budget. Spelling fixes and rename check the dictionary snapshots they relied on. Unknown resources stay unresolved. See [resource lookup and limits](docs/xaml-resource-resolution-plan.md) and [worker performance measurements](docs/xaml-language-performance.md).

**Wire event handlers.** Inside an event value such as `Click="OnSave"`, completion offers compatible instance methods from the root `x:Class`. Hover explains the handler and event; **F12** opens its C# definition. Missing methods, incompatible signatures and ambiguous overloads appear while editing, using the current C# compilation. At a missing or empty handler value, **Ctrl+. > Quick fixes > Create event handler** adds a compatible method to an identifiable authored partial class and fills an empty event value with a unique name. The action opens code-behind, preserves other source text and unsaved changes, and uses one **Undo workspace edit** operation. It changes buffers only; save normally. Changed source/context/selection, ambiguous or generated targets, and read-only files invalidate or withhold the action.

**Find and rename symbols across XAML and C#.** **Shift+F12** on a resolved binding property or event handler finds matching C# and XAML references, including closed XAML files. It also includes those XAML usages when invoked from C#. **F2** previews the C# rename together with verified binding-path and event-handler edits. Unrelated members with the same spelling remain separate. Open unsaved buffers take precedence, and the changes share one workspace undo without saving. Reference navigation checks the source snapshot and selects the corresponding XAML project context. Conflicting linked-file meanings, unavailable files, compiler conflicts, changed source during review and analysis limits withhold rename. Coverage notes explain design-type assumptions and unresolved runtime bindings; XAML type names, `x:Class`, other generator-derived members and reflection/string references still need separate review. Resource-key operations remain available through the same commands.

**Format and type XAML.** **Ctrl+Shift+F**, **Code > Format document**, and the editor menu format C# or XAML while preserving the current selection and unsaved edits. XAML formatting keeps quoted values, entity spelling, comments, inline text and `xml:space` content intact; it indents structural containers when their content model is known. Standalone files without project context use conservative rules for known framework containers. When project metadata is unavailable, local fallback preserves content spacing; unavailable or ambiguous owning-project contexts can also cause formatting to be skipped with an explanation. Malformed markup is left in place with an explanation. Typing assistance closes tags, pairs attribute quotes, completes a closing tag after `</`, and indents between matching tags. Generated text stays in the same typing undo step.

**Check XAML across projects.** Problems and WPF Explorer Issues include semantic diagnostics for evaluated XAML files even when their editors are closed. **Check XAML** in Problems or **Check project XAML** in WPF Explorer refreshes the scan. Open, unsaved XAML and C# take precedence over disk files. Closed files are reread, with file watching and a periodic refresh of known files; linked files retain separate results and project labels for each owning compilation. Opening a diagnostic checks its source snapshot before navigating and selects its project context. Build diagnostics remain visible separately from refreshed source findings.

The status shows analyzed file contexts, unavailable files and partial coverage. Each batch is bounded to 512 file contexts, 1,000,000 characters per XAML file, 8,000,000 total characters and 2,000 diagnostics. Missing, unreadable or over-budget model sources withhold affected type diagnostics rather than reusing stale symbols. Changes to project files, detected source membership or watched build configuration require **Reload workspace**; periodic refresh checks the existing evaluated inventory and does not discover every project change. See [analysis behavior and limits](docs/xaml-devtools-design.md#project-scans-and-linked-editor-contexts).

**Preview and inspect XAML.** Choose **Preview** in a XAML editor's context bar, **View > XAML Designer**, or the corresponding command-palette entry. The dockable pane renders in an isolated .NET 10 WPF process on an artboard sized from the root's `Width`/`Height` or `d:DesignWidth`/`d:DesignHeight`, fitted to the canvas; **Ctrl+wheel** zooms and the middle button pans. Hovering outlines authored elements, a click selects the authored element (**Ctrl+click** selects a template part), and the selection is mirrored in the XAML editor. While you type, the last frame stays visible until the new render lands, render errors appear in a banner over it with **Go to error**, and the selected element and property survive each re-render. Select a rendered element or tree node to inspect effective property values, their value sources, binding paths/status and observed failures; search the properties or show only values set on the element. See [working on the canvas](docs/xaml-preview-interaction.md#work-on-the-canvas). **Source** mode uses unsaved XAML, with linked visual/logical trees, selection outlines and authored source tags. **Update snapshot** rereads the existing view, tree, diagnostics and selected properties without recreating it; current preview state, temporary overrides and your property draft survive. Refresh and live preview recreate the view after edits; **Restart** recovers a stopped or failed host and reloads built custom controls. Source preview omits code-behind handlers, application startup and window chrome and reports those omissions.

**Experiment and apply.** **Try value** changes a supported scalar property temporarily; **Reset** restores it. **Write to XAML…** validates a literal value and opens a source diff; **Remove local XAML…** reviews removal of a local declaration. Applying changes the editor buffer, with **Undo workspace edit** available; save normally to write the file. The diff explains when a local value replaces a binding/resource/object declaration or affects every instance of a template. Changes preserve surrounding source and reject stale document versions and ambiguous property identities. Framework-generated elements and compiled views do not expose unchecked source writes.

**Interact with the preview.** Choose **Interact** to embed the existing WPF view at actual size, with native scrolling. Boundary Tab traversal hands focus back to the editor, and supported focused controls scroll into view while preserving newer manual scrolling. **Inspect** (or F8 in the view) detaches it and captures its current state without recreating controls, DataContext or temporary overrides. A background watchdog can stop a hung preview independently of the editor dispatcher, including unfinished focus handoffs. Native parenting can still briefly stall editor focus; physical input, IME, visible popups, mixed DPI and docking need broader validation. See [interaction behavior and limits](docs/xaml-preview-interaction.md).

**Preview a built view.** Select **Compiled**, check the full view type (initially its `x:Class`) and application resource path, then **Refresh**. Build the project first. This mode activates the built Window, Page or UserControl and its code-behind, with compiled `App.xaml` resources; leave the resource path blank for a library without an application resource. It displays the loaded assembly hash and module identity. Each refresh uses a fresh host and a public parameterless view constructor or an explicitly selected scenario view factory. It does not construct/run the project's App or execute its startup path, apply unsaved XAML or invent source locations for the build. Full compiled-design fidelity and Hot Reload remain outstanding. See [the architecture and remaining scope](docs/xaml-devtools-design.md).

**Inspect the running application.** Select a .NET 8, 9 or 10 WPF startup project, then choose **Debug > Run with XAML inspection** or **Debug with XAML inspection**. These explicit actions rebuild with XAML source information, preserve the launch profile, and load a small inspection agent before the target starts. The **Live XAML** pane shows actual visual/logical trees, DataContexts, binding status and source types, dependency-property values/origins, and bounded binding trace history. Simple missing CLR properties and failing MultiBinding children receive specific explanations; uncertain nested paths remain uncertain. Live refresh observes windows, popups and separate UI dispatchers. Inspection pauses with the debugger.

**Find and follow binding failures.** The **Binding issues** tab scans the tree without requiring you to select every element. Repeated failures are grouped with their individual instances; **Show element** opens the corresponding live bindings. Recovery requires a successful observation of the same binding expression. Removal, unloading, incomplete scans and disconnect do not count as recovery. Episode counts increase only when a verified recovery is followed by another observed failure. The scan and history are bounded, and incomplete coverage is displayed.

Preview and Live XAML share the selected binding's explanation in **Bindings**. **Cached path steps** shows WPF's resolved prefix and first unresolved step when supported; **Current binding details** shows the source kind, mode, converter and resolved owner/member. **Current validation** shows validation rules, messages and exception types. **Historical WPF evidence** separately records earlier missing-member, null-path and conversion notifications. The cached path reader does not evaluate model getters or converters. WPF can discard a failed segment's owner, so a null intermediate and a missing member cannot always be distinguished. WPF's normal expression lookup can initialize a dormant style binding. Select **Explain binding** on a preview diagnostic or **Show element** on a live issue to inspect that exact expression. See [binding explanations and their limits](docs/xaml-binding-diagnostics.md).

**Open the selected element's XAML.** Choose **Show XAML** in Live XAML. Navigation checks the loaded module identity, matching compiled symbols and resource mapping, stable build input, current file/editor text, and exact authored element position/type/name. Changed buffers, ambiguous owners or missing evidence produce an explanation instead of a guessed jump. **Verify source on build** is enabled by default and holds workspace XAML files stable through the inspected rebuild. Turn it off for custom build targets that rewrite those files; inspection still works, but verified source navigation and live source edits are unavailable for the next launch.

**Open the binding declaration.** In **Bindings**, choose a root or composite child in **Binding declaration**, then **Show binding XAML** to select its exact expression. Live binding issues expose the same action. The actual expression and declaration identities are checked again before navigation, preserving the property edit draft. Supported shared style bindings navigate to their setter. Code-created bindings, tested template clones, and source that cannot be verified receive an explanation. See [binding source navigation](docs/xaml-binding-navigation.md) for preview and runtime coverage.

**Pick an element.** Choose **Pick from app**, then click the element in the running application. The picking click is consumed before ordinary WPF control actions; press **Escape** in the application to cancel. Selection follows into the tree and Bindings tab. **Highlight selection** draws an outline when the target has a visible adorner surface, with an explanation when it cannot. Picking continues polling even when normal Live refresh is disabled. **Disconnect inspector** removes input handlers, adorners and the binding listener, restores inspector-owned property overrides where the dispatcher is responsive, and leaves the application running. Normal debugger Stop retains its process ownership behavior. The bundled debugger supports detaching from attached processes but cannot detach from a process it launched, so that action is disabled for launched sessions.

**Understand layout.** Select an element and open **Layout** in the XAML Designer or Live XAML. It shows observed desired/render/actual sizes, the parent-assigned layout slot, width/height limits, margins, alignment, transforms, DPI and clipping facts. Explanations call out conditions such as explicit dimensions, zero-size allocations, hidden/collapsed elements and pending layout. **Show layout overlay** draws the slot in cyan, render box in green, supported margin outline in orange and clip bounds in purple. Clip outlines are bounding approximations; they do not prove the exact visible region. Facts and outlines are snapshots: refresh after the application changes layout. Unsupported or stale geometry is explained, and changing selection, pausing or disconnecting clears stale details. Live overlays require a suitable adorner surface.

**Move and resize in the preview.** Enable **Edit layout** in Source/Inspect mode and select a supported direct Canvas or Grid child. Drag its frame or eight resize handles, using snap guides or Alt to bypass snapping. Arrow keys nudge, Shift uses ten DIPs, Ctrl+arrows resize, Enter reviews and Escape cancels. Applying the XAML review changes the unsaved buffer as one workspace edit. Canvas anchors and existing Grid tracks are preserved; unsupported source or layout contexts explain why editing is unavailable. See [layout editing](docs/xaml-preview-interaction.md#move-and-resize-authored-elements).

**Understand appearance.** Open **Appearance** in XAML Designer or Live XAML and choose a property. See the current WPF value source, relevant style and trigger declarations, available resource keys, local dynamic-resource keys and captured static-resource history. **Refresh appearance** updates the observation without applying the property draft. Declarations do not prove an active trigger, and historical lookups do not establish the current resource origin. See [appearance inspection](docs/xaml-appearance.md) for scope and limits.

**Try a live property value.** In the Live XAML **Properties** tab, select a supported property and edit its value; **Null** is distinct from empty text. **Validate** checks the typed value, **Try value** installs a temporary override, and **Reset override** restores the original local value or binding while preserving style/inheritance precedence. Preview and live inspection share the editing engine. Temporary overrides replace supported bindings without writing through their TwoWay sources. Application property callbacks can still run, and reset cannot undo their other effects. If the application replaces an override, its newer value is preserved. Stale observations require **Reload value**. An uncertain timeout offers **Check edit outcome** and blocks another edit instead of replaying a mutation. These operations do not change source files.

**Keep a live experiment in XAML.** In the same Properties tab, choose **Review XAML value…** to add or replace a local authored value, or **Review local removal…** to remove that declaration. The proposed value is checked against the actual dependency property and the type written in XAML, then shown in the normal source diff. The review explains replacement of bindings, resource expressions or object content, the effect of a local override on style/inherited values, and changes to a template shared by multiple instances. It preserves unrelated declarations, comments and namespace aliases. It does not edit the originating shared style or resource. **Null** writes a real XAML null using an existing language-namespace alias; empty text and removal remain different actions.

Live source edits require the same compiled/build/file/buffer verification as **Show XAML**, plus a current property observation. The checks run again after review, and changing selection, value, session, source or editor identity invalidates the pending edit. Apply changes only the editor buffer; save normally, or use **Undo workspace edit**. The command does not set the live property, reset a temporary override, rebuild or perform Hot Reload. Explicit proposed-value validation can run an application's dependency-property validation callback. Rebuild with inspection after saving to establish a new source baseline. Source validation is separate from temporary editing, so a supported property with OneWayToSource or a dynamic resource can still offer a reviewed source replacement even when **Try value** is unavailable.

OneWayToSource bindings, animations, dynamic resources and other unsupported expressions, rich TextBlock inline replacement, and complex object-content replacement are unavailable for temporary editing. The session retains at most 256 temporary properties and 1,024 edit-operation receipts; scalar input is limited to 65,536 characters. A blocked dispatcher can delay cleanup; an already executing property callback cannot be safely aborted. Classless resource dictionaries and code-created/generated content can lack verified source mappings; loose XAML hints do not authenticate how an object was created. Already-running uninstrumented applications, broader editing modes, fully attributed current path/conversion failures, trimmed applications and other runtimes need further work. See [runtime implementation and limits](docs/xaml-runtime-bootstrap.md) and [measured validation](VALIDATION.md).

**Build and debug.** Select the startup project, configuration, target framework, and launch profile. Restore, build, rebuild, clean, run, and test use the installed `dotnet` toolchain. Modified source documents are saved before build/debug; a failed save stops the operation. Click the C# editor gutter or press **F9** to toggle a breakpoint. Right-click the line and choose **Breakpoint > Condition** or **Enable / disable on this line**; **Debug > Show breakpoints** opens the list. Gutter markers and tooltips distinguish breakpoint state and show conditions. The Debug pane provides stack frames, threads, locals, watches, exception settings, and output. Attach by managed process ID. Stop ends a launched application; Detach releases an attached process.

**Understand WPF Explorer.** Open **View > WPF Explorer**. Its Components tab is a searchable index of your source: filter views and controls, view models, dictionaries, styles and templates, keyed resources, converters, or assets. Selecting an item explains its role and shows its source file; double-click to navigate. For a resource key, the details list XAML references that can be resolved to that declaration. Same-key references needing runtime context are counted separately. The Issues tab separates definite errors from informational cases that static analysis cannot settle. This is source analysis; controls are never instantiated.

Create paired view/view-model files, controls, dictionaries, or converters with **New item** and preview the generated files. Related-file navigation connects XAML, code-behind, and conventional view models. Right-click a resource to open its declaration or preview a key rename. Asset tools expose import, build actions, and pack URIs. Refresh the index after editing resource declarations. XAML assistance uses statically known types, resource keys, and DataContext information.

**Manage packages.** Open **Tools > NuGet packages**, choose the target project, and inspect Installed or search Browse. Select a version, optionally include prereleases, then explicitly install, update, or remove a reference. Package output shows restore failures and cancellation. Changes save modified documents first, use the project's `dotnet` SDK and NuGet configuration, and refresh the language workspace afterward. Central package versions are shown with a reminder that an update can affect other projects. Browse supports public NuGet V3 search; local or authenticated feeds can use an exact package ID/version through existing CLI credentials or credential providers. Install/restore respects all configured sources and source mappings. Use the terminal when a feed requires interactive sign-in.

**Use Git.** Open **Tools > Git changes** to inspect working and staged changes, view diffs, stage or unstage files, and commit the staged snapshot. History shows recent commits and their diffs. Create or switch branches, fetch, pull, or push through explicit commands. Pull is fast-forward only; branch changes and pull require a clean working tree. Save failures stop operations that first need current editor contents. Existing Git credentials are used without an interactive sign-in prompt; authenticate through the terminal if needed. Merge/rebase resolution and advanced repository administration remain terminal workflows.

**Ask ColtonGPT.** Open **Tools > Settings**, enter an OpenRouter API key, choose **Load models** or enter a model ID, then save. The key is protected for your Windows account under the local WpfStudio profile. Open **View > ColtonGPT** or **Ask ColtonGPT** from the editor menu. Choose no editor context, selected text, or the current document, and inspect **Preview exactly what will be sent** before sending with **Ctrl+Enter**. Messages and attached code go to OpenRouter and the selected model provider. Responses stream into the conversation; Stop cancels the request. The assistant cannot execute commands or edit files. Conversations remain in memory, and **New chat** clears history and editor-context sharing.

**Use the terminal.** Open Terminal, choose a shell, and create a session. Sessions retain their process across docking changes. Ctrl+C interrupts the active process; Ctrl+Shift+F searches scrollback. Closing a session cleans up its owned processes. The terminal uses local xterm assets, WebView2, and Windows ConPTY.

**Work with SQL Server.** Open SQL Server connections, enter a server/database, and choose Windows or SQL authentication. Encryption and certificate validation start enabled. Saving a SQL password is optional; remembered passwords are protected for the current Windows user. Connect refreshes the database list. Expand database objects on demand, select an object, and choose Use database or Open definition. The query target is always shown above the editor.

Create or open a SQL script, then explicitly Execute it. A selection executes only that selection; otherwise the full script executes. Ctrl+Space suggests SQL keywords and names from the schema objects you have browsed. Results are shown in separate grids, messages retain original script line numbers, and Cancel interrupts execution. Export CSV writes the displayed result set, including only displayed rows when a result is truncated.

Closing a modified SQL script prompts to save, discard, or cancel. Saving an opened script checks for external content changes before overwriting it, and an edit made while saving keeps the script open and dirty. Unsaved query tabs are saved to an atomic recovery file after a short typing pause; the SQL pane offers to restore them after an interrupted session. Recovery stores script text and file paths, including the previous saved text for conflict checks; it excludes connection passwords, results, and messages. Saving, discarding a tab, or completing a clean application close removes the corresponding recovery copies.

`GO` batches within one execution share a connection, so temporary tables and transactions work across batches. A new execution opens a new connection. `GO n`, SQLCMD directives, and SQLCMD variables are rejected before running the script. Results retain up to 10,000 rows or 16 MiB per result set, with at most 32 result sets and 64 MiB estimated display memory across one execution. The estimate includes row, column, and cell overhead so wide rows containing nulls still count. A single value retains up to 65,536 characters. Messages are limited to 1,000 entries or 256 KiB. Limits are shown explicitly; extra results are drained and later statements continue executing. These display limits never cancel SQL automatically. Table definitions show column declarations; keys and indexes can be inspected separately in the tree.

## Verify and package

```powershell
dotnet test WpfStudio.sln
./tools/Publish.ps1 -Zip
```

The publish script runs tests, publishes Windows x64 app and worker outputs, checks that Roslyn BuildHost, preview/inspection binaries, terminal assets, and debugger files exist, and writes the portable app under `artifacts/WpfStudio`. `-Zip` also creates `artifacts/WpfStudio-win-x64.zip`. Copy the complete directory and launch `WpfStudio.exe`; preserve `WorkspaceHost/`, `PreviewHost/`, `Inspection/`, `debugger/`, `Assets/`, and their dependency files, including the shared property-editing library. The default package requires the .NET 10 Windows Desktop runtime. `-SelfContained` includes that runtime but you still need the SDKs used to build your projects. `-SkipTests` is available for repeated local packaging after verification.

Before first launch, run `./Check-Prerequisites.ps1` from the portable folder (or `./tools/Check-Prerequisites.ps1` from the source repository). It checks Windows 11 x64, the .NET 10 SDK, the Desktop runtime or bundled runtime, and workspace-host files. Optional checks report missing WebView2, terminal assets, or debugger files with remediation links. It installs nothing. Use `-AsJson` for a machine-readable report, and `-ApplicationDirectory C:\Path\To\WpfStudio` to check another package; missing required components produce exit code 1.

Database tests cover batch parsing, DPAPI round-trips, display limits, CSV, view-model behavior, and WPF bindings. When LocalDB is installed, a uniquely named disposable instance verifies real SQL execution, authentication failures, cancellation, source-line mapping, and result truncation; it is deleted afterward. Other test projects verify document transactions, WPF analysis, workspace/language operations, and runtime features. Test output is the source of truth for any unavailable or skipped integration prerequisites.

Settings, layouts, recovery data, and SQL connection profiles live under `%LOCALAPPDATA%\WpfStudio`. Project sources remain in their original directories. Caches and optional feature processes are kept separate from the UI process where practical.

## Architecture and boundaries

| Project | Responsibility |
| --- | --- |
| `WpfStudio.App` | WPF shell, docking, editor, package/Git/ColtonGPT tools, application composition |
| `WpfStudio.Contracts` | Versioned documents, diagnostics, workspace edits, process-neutral interfaces |
| `WpfStudio.Core` | Document recovery/edit transactions, settings, WPF indexing and generation |
| `WpfStudio.Workspace` / `WorkspaceHost` | Named-pipe JSON-RPC, SDK/MSBuild discovery, Roslyn, build execution |
| `WpfStudio.Runtime` | Debug Adapter Protocol/netcoredbg and ConPTY/WebView2 terminal |
| `WpfStudio.Database` | SQL profiles, schema browsing, batch execution, bounded results, SQL pane |

This implementation targets SDK-style managed Windows x64 development. .NET Framework projects, native/mixed debugging, general visual composition and reparenting, inspection of already-running uninstrumented applications, full compiled-design fidelity, Hot Reload, and database administration remain outside the implemented scope. Preview currently runs on .NET 10; it does not establish fidelity for older runtimes or other process architectures. Opt-in running-app inspection uses a .NET 8 agent in .NET 8–10 WPF targets. Package management and common Git workflows have dedicated panes; advanced Git operations and private-feed interactive authentication use the terminal. Dynamic resources, runtime-created DataContexts, and application-specific markup extensions can prevent static XAML analysis from reaching a definite answer. C# rename cannot safely rewrite arbitrary string-based XAML bindings; review its warnings and preview. Refactoring actions are deliberately conservative rather than a complete Visual Studio code-fix catalog.

Performance goals are a usable shell within 2 seconds, a navigable 20-project/5,000-file tree within 5 seconds, warm completion below 250 ms at p95, and settled UI/worker memory below 1 GiB before optional features. These are measurement targets rather than unconditional guarantees; restore state, analyzer packages, SDK version, and hardware affect results.

Run `./tools/Measure-Performance.ps1` to generate a restored 20-project/5,000-source-file WPF fixture under `artifacts/performance`, measure worker load and 25 warm completion requests, and write `artifacts/performance/results.json`. This benchmark labels harness/worker memory separately; it does not substitute for measuring actual shell startup, first tree display, or optional terminal/debugger/SQL overhead.

The portable package includes `samples/CounterApp/CounterApp.csproj` for a small WPF/MVVM editing and debugging walkthrough. Open that project, build, set a breakpoint in `CounterViewModel.cs`, and press F5.

See [validation results and remaining manual checks](VALIDATION.md) and [third-party notices](THIRD-PARTY-NOTICES.md). `tools/Smoke-Portable.ps1` verifies the real published executable with an isolated settings directory; `WPFSTUDIO_DATA_DIRECTORY` can override the default profile for test runs.
