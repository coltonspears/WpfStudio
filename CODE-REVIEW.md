# WpfStudio code review: maintainability and bugs

Scope: all 16 projects under `src/` (about 52,000 lines of C#, 1,432-line `MainWindow.xaml`). Reviewed against the five concerns raised: coupling, single-responsibility, DI registration, async practice, and code-behind versus MVVM. Line numbers are 1-based and were checked by reading the file at review time (branch `claude/csharp-wpf-review-c172f8`, commit `6a02e5c`). Items marked **possible** were not reproduced and depend on runtime conditions.

## Overall assessment

The architecture is sound in its bones: Microsoft.Extensions.Hosting composition, CommunityToolkit.Mvvm source generators, an `IUiDispatcher` abstraction that keeps most view models off `System.Windows.Threading`, out-of-process Roslyn/preview/profiling hosts behind interfaces, and a large test suite (Shell, Workspace, Preview, Inspection) that constructs the real view models. Views are thin: total code-behind across the solution is about 1,100 lines.

The maintainability cost is concentrated in a few places:

1. **One hub object.** `ShellViewModel` is 4,921 lines across 26 partial files, takes 18 constructor parameters, wires every feature by hand, and carries unrelated responsibilities (auto-save, command palette, task list, file groups, external-change review, XAML analysis scheduling, inspection launch, settings). Other feature view models follow the same pattern (`DesignerViewModel` 14 partials, `InspectionViewModel` 9, `MemoryProfilerViewModel` 9).
2. **Untyped glue.** Features talk to the shell through mutable `Func<>` properties, multicast `Func<..., Task<T>>` "events" that only work with one subscriber, string tool ids (`"Output"`, `"Debugger"`, `"Git"`) repeated in 18 call sites plus a behavior and a converter, and `Status` text compared as state.
3. **Static globals.** Theme, editor preferences, desktop navigation, MSBuild registration and several test knobs are process-wide mutable statics outside the container.
4. **No safety net for async faults.** There is no `DispatcherUnhandledException` or `UnobservedTaskException` handler in the main app, several `[RelayCommand]` methods and `async void` handlers are unguarded, and there are more than 100 `_ = SomethingAsync()` sites, not all of which route through a guard.
5. **House style.** Many statements per line (`IsBusy = true; _loading = true; _operation = new();`) is consistent, but it defeats line-level breakpoints, makes diffs noisy, and hides control flow in `if (x) { a; b; c; }` one-liners. No analyzers are enabled in `Directory.Build.props`.

CommunityToolkit.Mvvm is used consistently for properties and commands; what is missing is the declarative dependency attributes around them and two toolkit features that are not used at all, the cancel commands for the long operations and the messenger (1.6). The C# 14 `field` keyword is not used yet; the few explicit backing fields that remain are listed in 1.7.
